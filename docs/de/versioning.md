# Versionen, Commits und Updates

[Handbuch](README.md) · [English](../en/versioning.md) · [Projektübersicht](../../README.md)

Das Format ist **`MAJOR.MINOR.REVISION[-PATCH]-ALPHA`**; `ALPHA` ist immer enthalten. Die Version steht rechts im Footer. Ausgangspunkt ist `0.0.0-ALPHA`, festgelegt in `../../version.json` mit einem Git-Basiscommit.

- Jeder Commit mit `feat:` oder `feat(bereich):` erhöht die **Revision** und setzt den Patch auf 0 zurück.
- Jeder Commit mit `fix:` oder `fix(bereich):` erhöht den **Patch**. Patch 0 wird nicht angezeigt: `1.0.3-ALPHA` → Fix → `1.0.3-1-ALPHA` → Feature → `1.0.4-ALPHA`.
- Andere Commit-Typen ändern die Nummer nicht. Merge-Commits werden nicht doppelt gezählt. Auch `feat!:` und `fix!:` erhöhen ausschließlich Revision bzw. Patch; Major und Minor bleiben manuell.
- **Major/Minor manuell:** `npm run version:major` bzw. `npm run version:minor` (mit Bun: `bun run version:major:bun` / `bun run version:minor:bun`). Diese Befehle setzen Revision/Patch zurück und speichern einen neuen Basiscommit. Danach die geänderten Versionsdateien beispielsweise mit `chore: manuelle Minor-Version erhöhen` committen. Ein Major-Sprung setzt zusätzlich Minor auf 0.
- Die App prüft beim Start, alle fünf Minuten in sichtbaren Tabs sowie bei Rückkehr zum Tab oder Wiederherstellung der Verbindung die Frontend-Inhaltsversion ohne Browser-Cache. Bei einem anderen Hash bietet sie „Jetzt laden“ oder „Später“ an, auch bei einem Rollback. „Später“ unterdrückt diesen Hash bis zum nächsten Seitenaufruf. Reine App-/Backend-Versionsänderungen lösen kein Frontend-Update aus. Im Vite-Entwicklungsmodus übernimmt Hot Reload die Aktualisierung.
- `node scripts/version.js` bzw. `bun run version:current:bun` zeigt die berechnete Version. Lokale Builds und Vite berechnen sie automatisch aus der vollständigen Git-Historie. Ein Commit erhöht die Nummer erst beim nächsten Build/Neustart des Vite-Servers; bloße Dateiänderungen tun das nicht.
- Die Docker-Pipeline berechnet die Nummer einmal und verwendet denselben Wert für Footer, Backup-Metadaten, OCI-Label und den vollständigen Image-Tag, etwa `ghcr.io/drganmon/aquarium-logbuch:1.0.4-2-ALPHA`. Die Versions-Tags werden auf dem Default-Branch und bei passenden `v…`-Release-Tags veröffentlicht; `latest`, Branch- und SHA-Tags bleiben verfügbar. Pull Requests veröffentlichen keine Images.
- **Compose fest auf eine Version setzen:** `AQUARIUM_VERSION=1.0.4-2-ALPHA docker compose --project-directory . -f docker/docker-compose.yml up -d`; alternativ `AQUARIUM_VERSION` in `.env` setzen. Ohne Angabe wird weiterhin `latest` verwendet.
- **Lokales Docker-Image:** `APP_VERSION=$(node scripts/version.js)` und danach `docker build -f docker/Dockerfile --build-arg APP_VERSION="$APP_VERSION" -t "aquarium-logbuch:$APP_VERSION" .`. Ohne Git-Historie und ohne explizites `APP_VERSION` wird nur der in `../../version.json` hinterlegte Ausgangswert verwendet. Eine unvollständige Historie in einem Git-Checkout verursacht einen Fehler statt einer falschen Versionsnummer.

## Eigene Frontend-Version

Der Build erzeugt `public/dist/frontend-version.json` mit `{schema:1,version,assets}`. `version` ist ein SHA-256-Hash der ausgelieferten JavaScript-/CSS-Dateien einschließlich Web Worker, des Service-Worker-Quelltexts und der Offline-Shell (HTML-Vorlage, Manifest und Icons). `assets` enthält Inhaltsversionen pro Cache-Datei. Die Reihenfolge ist deterministisch; App-Version und Source Maps gehen nicht ein. Änderungen an gemeinsam genutztem Code ändern die Frontend-Version, wenn sie das Browser-Bundle verändern. Die Datei wird automatisch erstellt und nicht manuell gepflegt oder committet.

`dist/version.json` bleibt für die allgemeine App-Version erhalten und enthält zusätzlich `frontendVersion`. Der Footer liest die App-Version aus HTML-Metadaten und aktualisiert sie beim Versionsabruf; die App-Version ist nicht mehr ins JavaScript eingebaut. Die HTML-Metadaten identifizieren zugleich die tatsächlich geladene Frontend-Fassung. Beim Versionsabruf wird nur die kleine Metadatendatei geladen, nicht das gesamte Frontend.

Der neue Service Worker kopiert Dateien mit gleicher Inhaltsversion aus dem vorherigen Cache und lädt geänderte Dateien nach. Erst eine vollständige Installation ist aktivierbar. Während der Vorbereitung bleibt der Update-Button gesperrt; ein abgebrochener Download ersetzt den aktiven Offline-Stand nicht. „Jetzt laden“ erlaubt die Aktivierung der angebotenen Fassung und lädt anschließend nur diesen Tab neu. Laufende Messungen vorher abschließen und Eingaben speichern. Es gibt kein erzwungenes Neuladen während der Benutzung; ein wartendes Update kann vom Browser regulär aktiviert werden, nachdem alle bisherigen Tabs geschlossen wurden.

HTML und zugehörige Dateien werden aus derselben Cache-Fassung ausgeliefert. Andere offene Tabs behalten Zugriff auf ihre bisherige Fassung, einschließlich später geladener Ansichten. Alte Shell-Caches werden entfernt, sobald alle offenen Tabs ihre Fassungen gemeldet haben und die Dateien nicht mehr benötigen. Unbekannte Tabs verhindern eine vorzeitige Bereinigung. Kontogetrennte IndexedDB-Daten und Bild-/Katalog-Caches bleiben erhalten. HTTPS bzw. localhost und ein erfolgreicher erster Online-Start sind für Service Worker erforderlich. Docker Compose benötigt keine Anpassung.

Der Update-Button prüft die Inhaltsversion des tatsächlichen Service Workers. Wurde die angebotene Fassung bereits in einem anderen Tab aktiviert, kann dieser Tab sie weiterhin mit „Jetzt laden“ übernehmen. Die Cache-Bereinigung pausiert, solange ein weiterer Service Worker installiert wird oder auf Aktivierung wartet.
